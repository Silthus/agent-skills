# Orchestration Wayfinder — T3 Code threads

Read this addendum when the conductor runs inside T3 Code, together with the runtime addendum.

By default, every lane the conductor manages runs as a **T3 subthread** (`delegate_task` with `mode: "async"`) so it stays under the conductor's lineage and out of the sidebar: `research`, `task` (AFK or HITL), `spec`, and `implement` (stacks and standalone pull requests). Only **live human-conversation lanes** — `grilling` and `prototype` — launch as top-level sidebar threads (`t3_thread_launch`), because the human chats in them directly, one at a time on the conductor's cue. Every other lane parks with the conductor, which asks for it, watches its pull requests, and merges for it, per **Human contact** and **Merge** in [`SKILL.md`](SKILL.md).

## Every wake

Run this checklist first on every conductor wake, a sweep run included:

1. **After a compaction**, load the deferred tools the lanes need before anything else (in Claude Code, `ToolSearch` for every T3 tool this file names), reread the [`t3-kickoff`](../t3-kickoff/SKILL.md) skill and the **lane file**, and run **Recovery**.
2. Run one lanes command: `fleet lanes <map URL>` when the `fleet` CLI is available, otherwise check each open subthread with `task_status` / `t3_thread_read` and each live sidebar thread with `kickoff status` under **Wake**. Act on each line it prints per **Wake**.
3. List pending requests with `t3_pending_request_list`, and cue each new one on a thread in the lane file per `blocked` under **Wake**.
4. Check `list_scheduled_tasks`: keep exactly one sweep bound to this thread while the **Sweep** rule in **Wait out of the inbox** holds, create it when missing, and delete it once the rule no longer holds.
5. An **empty wake**, with no notice and nothing found in steps 2 to 4, is those commands and a one-line status ending on the `⏳` line.

The **lane file**, `$(git rev-parse --git-common-dir)/wayfinder/<map>/lanes.md` in the conductor's checkout, lists every open lane: its ticket, type, runtime (`subthread` or `thread`), full thread id (or `childThreadId` and latest `taskId`), and title. Update it with every locator you record, drop a lane when its ticket closes, and rebuild it from the tickets' locator comments when it is missing. A compaction summary carries each open lane's full ids and the sweep's task id.

The thread status and stop commands for top-level sidebar threads come from the [`t3-kickoff`](../t3-kickoff/SKILL.md) skill. Read it before launching a `grilling` or `prototype` thread. Below, `kickoff` means `bun <t3-kickoff skill directory>/scripts/kickoff.ts`.

## Cast

Both T3 subthreads (`delegate_task`) and top-level T3 threads (`t3_thread_launch`) run their model natively through T3. Neither is a provider bridge, so the retired-cast rule in [`SKILL.md`](SKILL.md) does not apply to the lane's own model.

Follow **Casting** in [`SKILL.md`](SKILL.md) to choose the worker's model, then call `orchestrator_capabilities` once per conductor thread to resolve the provider offering it:

- For `delegate_task`, pass `target` with `providerInstanceId`, `model`, and `options` (for effort), so the conductor's own model does not replace the selection. Omit `runtimeMode` locally to inherit the conductor's mode; pass `runtimeMode: "full-access"` on any linked environment (`target.environmentId`).
- For `t3_thread_launch` (`grilling` and `prototype`), pass `modelSelection` with `instanceId`, `model`, and `options`.

When the `fleet` CLI is available (on `PATH` or at `~/dev/fleet/fleet`), read `fleet availability`, the live-quota report all maps share, before a dispatch; without it, keep the runtime's own provider checks. Defer a family reported as `exhausted`, and keep the user's chosen model. The family is `claude` for `claude-*` models and `codex` for `gpt-*` models. `unknown` requires the normal live check. Otherwise dispatch the whole frontier at each wake. Do not cap parallel workers to save subscription quota, and ignore any such concurrency note in the map's **Notes** or another thread.

## Conductor address

Before the first dispatch, get the conductor's thread id and title from `t3_thread_configuration` (or `t3_thread_configure`) without a `threadId`. Write them as the `Conductor` line of the **Stacks board** in [`SKILL.md`](SKILL.md). A new conductor after a handoff or resume updates this line before it does anything else. Live sidebar threads read the line when they notify, so a conductor change never strands them. Subthreads report back to the thread that delegated them: before handing off to a new conductor thread, let active child tasks finish (or record their `childThreadId` and pushed branches on their tickets), dispatch no new child task, and delete the sweep with `delete_scheduled_task`. On the new conductor, continue an idle subthread with `t3_thread_send` or start a successor subthread from its pushed branch.

## Start a subthread (`research`, `task`, `spec`, `implement`)

1. Render the worker prompt to a file per [`LANE.md`](LANE.md). Its template adds the ticket type's terminal and tells the worker that it never asks the human directly and parks with the conductor instead.
2. Start it with `delegate_task` on the conductor's machine:
   - `title`: `<type> #<id>: <ticket title>`
   - `mode`: `"async"`
   - `isolation`: `"worktree"` for any writer (`spec`, `implement`, writing `task`, writing `research`); `"shared"` (or omit) for read-only work. `delegate_task` with `isolation: "worktree"` runs on the conductor's machine and starts from the parent commit, so the prompt tells the worker to fetch `origin` and branch from `origin/<default>` (or from its predecessor's pushed branch for a successor).
   - `target`: per **Cast** above.
   - `task`: the rendered prompt.
   Done when it returns `taskId` and `childThreadId`.
3. Record the locator on the ticket immediately:

   ```md
   <!-- orchestration-wayfinder-dispatch -->

   Runtime: T3 Code
   Task: <taskId>
   Child thread: <childThreadId>
   Title: <thread title>
   ```

4. For an `implement` ticket, set its board row's Thread to `[<title>](t3-thread://v1/<childThreadId>)` and its State to `building`.

A subthread survives a conductor restart and wakes the conductor automatically when its turn ends, so arm no waiter and do not poll `task_status`. End the turn per **Wait out of the inbox** below.

## Start a live sidebar thread (`grilling`, `prototype`)

Only `grilling` and `prototype` lanes — where the human chats directly with the worker — launch as top-level sidebar threads:

1. Render the worker prompt to a file per [`LANE.md`](LANE.md). Its template adds the ticket type's terminal and **Notify and settle** below, and tells the worker that the human talks to it in this thread.
2. Launch it with `t3_thread_launch` in the code repo's T3 project, per **Map tracker** in [`SKILL.md`](SKILL.md): `title` `<type> #<id>: <ticket title>`, `modelSelection` per **Cast**, `workspaceStrategy` `{ type: "worktree", baseRef: <base>, startFromOrigin: true }` (or `startFromOrigin: false` for a local base), and the prompt as `message`. Pass `branch` when the ticket has a fixed one, such as `prototype/<name>`. Done when it returns the thread id. After an error or a lost reply, look for the thread with `t3_thread_list` before launching again.
3. Record the locator on the ticket immediately:

   ```md
   <!-- orchestration-wayfinder-dispatch -->

   Runtime: T3 Code
   Thread: <threadId>
   Title: <thread title>
   ```

4. Grilling only: grilling is live from the first turn, so cue the human with the thread title when no other live lane holds the cue (**Live lanes** in [`SKILL.md`](SKILL.md)), else when that ticket closes. Record `<!-- orchestration-wayfinder-cue:t3:<threadId> -->` on the ticket.

Arm no waiter. The thread reports to the conductor itself. End the turn per **Wait out of the inbox** below.

## Terminals

**Grilling (live sidebar thread).** The worker grills the human live in the thread with the `grilling` and `domain-modeling` skills. When the tree is exhausted, it posts the durable handoff comment, closes the ticket, notifies and settles, and ends its turn with a one-line summary.

**Prototype (live sidebar thread).** The worker builds the prototype with the `prototype` skill, or `architecture` for an architecture prototype, on its `prototype/<name>` branch in its AFK stretch, then parks: the park comment, `wayfinder:awaiting-human`, a park notice, and a thread message. For a prototype from the `prototype` skill, the message carries the link the `prototype` skill hands over and names the one question it answers. For an architecture prototype, the pending question is its first `architecture` round, and both the message and the park comment are that round in full, per **Rounds** and **Render the diagram** in `architecture`. Its branch stays empty until capture, so until then the thread message links only the ticket and the ticket comment has no links line. A `prototype` skill preview is a systemd unit outside the thread, so it stays up through the park; the **lane rules** in [`LANE.md`](LANE.md) cover what runs in the thread. When a reply finds the preview stopped, restart it per `share-preview` before iterating. Each human reply is feedback. A `prototype` skill worker iterates, pushes, and ends its turn. An architecture worker posts its next round in the thread and as a new ticket comment, ends its turn, and pushes its branch at capture. The human's explicit acceptance is the only resolution. On acceptance, the worker pushes the branch, posts the durable handoff with the decision, the branch pointer, and, for a UI prototype, its element checklist per the `prototype` skill, removes `wayfinder:awaiting-human`, closes the ticket, and notifies and settles.

**Stack (`implement` subthread).** The worker follows **Stack thread** in [`SHIP.md`](SHIP.md). In T3 Code, delegated children cannot call `watch_pull_request` (the server rejects subagent watches), so the subthread never calls `watch_pull_request`. Instead:

1. The subthread branches off fetched `origin/<default>` in its own worktree, builds and proves its slice(s), links each pull request with `link_pull_request`, posts its state or handoff comment on the ticket, and ends its turn with its last line naming every open pull request, head SHA, and state (`PR <url>, head <sha>, <state>`) — or `NEEDS_HUMAN: <question>, from the human via the conductor` when parked.
2. Ending the turn wakes the conductor. The conductor links each open pull request (`link_pull_request`) and holds `watch_pull_request` on it while CI, reviews, approvals, or conflicts are pending.
3. Whenever a PR watch wakes the conductor (a check fails, checks pass and ReviewHog/StampHog/gate needs to run, a new review comment or conflict lands), or when the human answers a question, or when the conductor merges a PR (`merged <owner/repo#n> <merge sha>`), the conductor wakes the **same** subthread with `t3_thread_send` (`threadId: <childThreadId>`, `mode: "auto"` or `"queue"` when a turn is active). `t3_thread_send` on a finished child thread starts a fresh delegated task in that subthread's existing worktree and returns its new `taskId`; record the new `taskId` in the lane file.
4. When a pull request passes the ready gate and is approved on its head, the subthread reports `stack <name>: approved <owner/repo#n>@<full head sha>...` with its proof link and ends its turn; the conductor keeps the PR watch and puts the stack on its next merge card per **Merge** in [`SKILL.md`](SKILL.md).
5. When the conductor sends `merged <owner/repo#n> <merge sha>`, the subthread runs `rollout` from Deploy, resolves the ticket once the whole stack is `done`, and ends its turn.

**Research, `task`, `spec`, stack parks, and successors (subthreads).** The worker runs its AFK stretch with its prescribed skill, and a successor continues from its predecessor's pushed branch and park comment. When it needs the human, it parks per **Human contact** in [`SKILL.md`](SKILL.md): push its branch when it has one, post the park comment with its decision lines and one pending question (recommended answer first), add `wayfinder:awaiting-human`, ask no question card, and end its turn with a final message ending on `NEEDS_HUMAN: <the question>, from the human via the conductor`. Ending the turn completes its delegated task and wakes the conductor — the subthread stays in the conductor's lineage and does **not** move to a top-level sidebar thread. When the conductor relays the human's answer back to the same `childThreadId` via `t3_thread_send`, the subthread records the decision on the ticket and continues to the next park or to resolution. On resolution, it posts the durable handoff, removes `wayfinder:awaiting-human`, closes the ticket, and ends its turn.

## Notify and settle (live sidebar threads only)

Every `grilling` and `prototype` prompt includes these steps. The thread sends a notice only on a tracker transition, never on an ordinary conversation turn:

- **First park** → after the park is durable, send the conductor `<type> #<id> parked` with `t3_thread_send`, `mode: "queue"`, to the thread on the map body's `Conductor` line. Queue mode keeps a question card that the conductor waits on; any other mode cancels it.
- **Closed** → after the ticket is closed, send the conductor `<type> #<id> closed` the same way. Then call `t3_thread_organize` with `action: settle` and no `threadId`. The thread settles when its turn ends and leaves the human's active list.

If the send fails, the thread still settles. The conductor finds the closed ticket at its next frontier query. Subthreads need neither step: ending their turn wakes the conductor directly, and they stay under lineage instead of the sidebar.

## Wait out of the inbox

The inbox means the human must act. End every conductor turn in one of two ways:

- **Nothing for the human to act on** → keep `watch_pull_request` armed on every open pull request of the map's subthread stacks, and end on `⏳ **Waiting on** <its lanes, PR watches, or the exhausted family, named>`, such as `⏳ **Waiting on** the #337 and #338 lanes`. This includes a turn that ends with a status update, a relayed result, or an answer to the human's question. The thread snoozes: when the `fleet` CLI is available, its Stop hook snoozes it for 3 days; otherwise snooze it yourself (`t3_thread_organize`, `action: snooze`, `snoozedUntil` 3 days ahead). A subthread completion, PR watch wake, or live-thread notice wakes the conductor; handle it and end the same way.
- **The human must act**: a cue, a question, an approved merge card, an orchestration blocker, or done → when the thread is snoozed, unsnooze it first (`t3_thread_organize`, `action: unsnooze`), then end with the card or the closing form that fits. Done is the final report and the retro card, per **Conductor loop** in [`SKILL.md`](SKILL.md), which keeps the thread open. When one turn has both a status update and an action, the action decides. A turn that ends while a conductor question or orchestration blocker is still unanswered counts as an action turn. Do **not** hold a question card waiting for unrelated long-running subthread lanes to finish: a pending question card brings the conductor to the human's inbox even while sibling subthreads keep running.

**Sweep.** A lane can stall without a notice, a PR watch can drop, and a deferred family can come back. While a lane is open or a ticket waits on an exhausted family, keep one `schedule_task` bound to the conductor (`bindToCurrentThread: true`, `schedule: { type: "interval", everyMs: 7200000 }`) with the prompt `Run **Every wake** in the orchestration-wayfinder skill's T3.md and act on what it finds. With nothing for the human and no question open, end on the ⏳ line; with one open, restate it in full.` Record its task id in the lane file. A scheduled run queues, so it never cancels a pending card.

## Wake

A subthread completion, a PR watch wake, or a live-thread notice is a worker notification. Apply the **Wake law** to the tracker first, then act on the ticket:

- **Closed** → verify the durable handoff. For a live sidebar thread (`grilling` or `prototype`), verify that `t3_thread_list` with `settled: true` lists it, and settle it with `t3_thread_organize` (`action: settle`, its `threadId`) if not. For a subthread stack, verify every PR is merged or closed and no stale watch remains. Drop the lane from the lane file.
- **A stack subthread ended its turn with an open PR** → read its result (and update the Stacks board row and map comment on state changes, per **Stacks board** in [`SKILL.md`](SKILL.md)). Link each new pull request (`link_pull_request`) and call `watch_pull_request` on it while CI, reviews, approvals, or conflicts are pending.
- **A PR watch woke the conductor** → read the PR live. If it needs action (failing CI, new review comment, merge conflict, required checks passed and ReviewHog/StampHog/gate needs to run), wake its stack's `childThreadId` with `t3_thread_send` (`mode: "auto"`), naming the event, head SHA, and PR URL, and update the lane file with the returned `taskId`. Keep the watch armed unless the PR merged or closed.
- **Open, first `wayfinder:awaiting-human`** → a `grilling` or `prototype` live thread: cue it per **Live lanes** in [`SKILL.md`](SKILL.md) and record the `t3` cue marker. Any subthread (`research`, `task`, `spec`, `implement`): put its pending question on the conductor's card, per **Human contact** in [`SKILL.md`](SKILL.md).
- **A stack's `approved` report** → put its rows on the conductor's card and enqueue what the human selects, per **Merge** in [`SKILL.md`](SKILL.md). After a merge, wake the stack's `childThreadId` with `t3_thread_send` (`mode: "queue"`, `merged <owner/repo#n> <merge sha>`).
- **The human answered a card** → relay each answer to its subthread (`t3_thread_send` to `childThreadId` with `mode: "auto"` or `"queue"` if busy, the answer word for word and the question it answers, plus `environmentId` when on another machine) and record the returned `taskId` in the lane file. For a live sidebar thread, unsettle it first if settled.
- **Open, any other state** → leave the lane alone.

`fleet lanes` prints one line per claimed lane, subthread or sidebar thread, that is `finished`, `needs the human`, `stalled`, `blocked`, or `gone`, and one per devbox that did not answer. Where `task_status` disagrees, trust `fleet lanes`.

- **`finished`** → the lane ended its turn with its ticket open. A stack subthread whose board state is `building`, `ready`, `approved`, `merging`, or `rolling-out` is waiting on the conductor's PR watch (or merge card): verify this conductor still holds `watch_pull_request` on its open PRs and check if a PR event was missed; if nothing is owed, leave it. Otherwise read its result (`t3_thread_read`) and take the ticket's next step: send the worker what it is missing via `t3_thread_send`, or reconcile the lane as orphaned when it left no durable report.
- **`needs the human`** → the lane ended its turn with a `NEEDS_HUMAN:` line. Unless the ticket carries `<!-- orchestration-wayfinder-cue:t3-needs-human:<threadId> -->`, put the ask on the conductor's card per **Human contact** in [`SKILL.md`](SKILL.md), then record that marker. Relay the answer to its thread via `t3_thread_send`, and remove the marker, so the lane's next ask gets its own question.
- **`stalled`** → past its cap, stop a subthread with `task_cancel` (using its `taskId`, never `t3_thread_interrupt` on a `childThreadId`) or a live sidebar thread with `kickoff stop`, mark it orphaned, and reconcile per the lane contract. Under its cap, check it again at the next wake.
- **`blocked`** → the thread after `in thread` waits on a request. Unless the ticket carries `<!-- orchestration-wayfinder-cue:t3-blocked:<that threadId> -->`, cue the human with that thread's title and its request, then record that marker.
- **`gone`** → the `gone: true` case below.
- **A devbox did not answer** → run `fleet lanes` once more. Still silent → its lanes stay unchecked; check each open `Child thread` with `t3_thread_read` and each open live `Thread` with `kickoff status` below.

Without `fleet lanes`, check each open lane whose last durable activity is older than 15 minutes on every wake and before completion (`task_status` / `t3_thread_read` for subthreads; `kickoff status --thread <threadId>` for live sidebar threads):

- **`state` is `running` and `startedAt` is older than the cap** → `task_cancel` (subthread) or `kickoff stop --thread <threadId>` (sidebar thread), mark the lane orphaned, and reconcile per the lane contract.
- **`state` is `failed`, its `error` names a usage or rate limit, and its family has lanes above `0`** → the hub's resume sweep passed it over. For a subthread, wake it with `t3_thread_send` (`Continue where you left off.`) once its provider is available, or reconcile as orphaned if it fails again. For a sidebar thread, settle it with `t3_thread_organize` (`action: settle`, its `threadId`), then mark it orphaned and reconcile.
- **`gone: true` with the ticket open** → the thread was archived or deleted. Mark the lane orphaned, reconcile the ticket per the lane contract, and cue the human once to ask whether to redispatch it.
- **Status check fails twice** → the T3 server did not answer. Record an orchestration blocker on the map and cue the human once.

## Recovery

Both T3 subthreads and live sidebar threads survive a conductor resume. A ticket whose latest locator says `Runtime: T3 Code` recovers here, not through the runtime addendum.

Update the map body's `Conductor` line first. Then reconcile the tracker:

- For a `Child thread` / `Task` locator: read `task_status` (or `t3_thread_read` if `taskId` is stale after restart). A live task stays. A finished subthread with `wayfinder:awaiting-human` stays parked for the conductor's card. A finished `implement` subthread with open PRs needs the conductor's `watch_pull_request` re-armed on each open PR. Any other terminal subthread whose ticket is still open with no durable report is orphaned: reconcile it per the lane contract.
- For a live `Thread` locator (`grilling` or `prototype`): continue at step 2 of **Every wake**.

An invalidated ticket: record the invalidation, clear `wayfinder:awaiting-human`, and either call `task_cancel` on a running subthread (and unwatch any PRs it opened if closed) or `kickoff stop --thread <threadId>` then `t3_thread_organize` (`action: settle`, its `threadId`) for a live sidebar thread.
